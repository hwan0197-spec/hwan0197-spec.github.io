광고를 눌러 들어온 손님이 하얀 화면만 보다가 뒤로 가기를 누르면, 광고비는 나갔는데 상담 신청은 0건입니다. 특히 휴대폰은 와이파이가 아닐 때도 많아서, 내 컴퓨터에서 빠르게 열리던 페이지가 손님 휴대폰에서는 답답할 수 있어요.

이 글은 **무료로 속도를 재는 법**, **결과 화면에서 무엇을 봐야 하는지**, **작은 가게 페이지에서 자주 걸리는 원인** 순서로 정리했습니다.

> 아래 지표 기준과 데이터 설명은 2026년 10월 5일에 Google 공식 문서([web.dev – Web Vitals](https://web.dev/articles/vitals), [PageSpeed Insights 소개](https://developers.google.com/speed/docs/insights/v5/about))에서 확인했습니다.

## 1. PageSpeed Insights로 재는 순서

Google이 무료로 제공하는 [PageSpeed Insights](https://pagespeed.web.dev/)를 쓰면 됩니다.

1. 사이트에 들어가 내 페이지 주소를 붙여 넣고 분석을 누릅니다.
2. 결과가 **모바일**과 **데스크톱**으로 나뉘어 나옵니다. 광고 손님은 대부분 휴대폰으로 보니 **모바일 결과부터** 보세요.
3. 첫 화면만 재지 말고, 광고나 QR이 연결되는 **실제 랜딩페이지 주소**를 넣으세요.

## 2. 결과 화면의 두 가지 데이터

결과 화면에는 성격이 다른 데이터 두 종류가 나옵니다. 이걸 구분하지 않으면 숫자가 왜 다른지 헷갈립니다.

| 구분 | 무엇인가 | 언제 보나 |
|---|---|---|
| 실제 사용자 데이터 | Chrome 사용자들이 지난 28일 동안 실제로 겪은 속도 | 방문자가 충분히 쌓인 뒤 |
| 실험실 데이터(점수) | 정해진 기기·네트워크 조건에서 한 번 불러와 본 결과 | 지금 바로, 고친 뒤 비교할 때 |

공식 문서에 따르면 막 만든 페이지나 방문자가 적은 페이지는 실제 사용자 데이터가 **충분하지 않아 표시되지 않을 수** 있습니다. 작은 가게 사이트라면 이 경우가 흔하니 당황하지 마세요. 그럴 때는 아래쪽의 실험실 데이터와 개선 제안을 보면 됩니다.

실험실 점수는 같은 페이지라도 잴 때마다 조금씩 달라집니다. 한 번 숫자에 일희일비하지 말고, **고치기 전과 후를 두세 번씩 재서** 비교하세요.

## 3. 점수보다 먼저 볼 지표 3가지

Google은 사용자 경험을 보여 주는 핵심 지표(Core Web Vitals)로 세 가지를 꼽습니다. web.dev가 안내하는 '좋음' 기준은 다음과 같습니다.

| 지표 | 쉽게 말하면 | 좋음 기준 |
|---|---|---|
| LCP | 화면에서 가장 큰 내용(대표 사진, 큰 제목)이 뜨기까지 걸린 시간 | 2.5초 이하 |
| INP | 버튼을 눌렀을 때 화면이 반응하기까지 걸린 시간 | 200밀리초 이하 |
| CLS | 읽는 도중 내용이 갑자기 밀리는 정도 | 0.1 이하 |

기준은 방문의 **75퍼센타일**, 즉 방문자 4명 중 3명 이상이 이 기준 안에 들어와야 '좋음'으로 봅니다. 휴대폰과 데스크톱은 따로 평가합니다.

작은 가게 랜딩페이지는 기능이 단순해서 INP보다 **LCP와 CLS**에서 문제가 생기는 경우가 많습니다.

## 4. 자주 걸리는 원인과 고치는 법

**대표 사진이 너무 큽니다.** 휴대폰으로 찍은 원본 사진을 그대로 올리면 파일 하나가 수 MB가 되기도 합니다. 화면에 보이는 크기에 맞게 줄이고, 압축해서 올리세요. 이것 하나로 LCP가 크게 좋아지는 경우가 많습니다.

**아래쪽 사진까지 한꺼번에 불러옵니다.** 첫 화면에 안 보이는 후기·포트폴리오 사진에는 `loading="lazy"`를 붙이면 스크롤할 때 불러옵니다. 단, 첫 화면 대표 사진에는 붙이지 마세요. 오히려 늦게 뜹니다.

```html
<img src="review-01.jpg" width="600" height="400" loading="lazy" alt="수강생 후기 사진">
```

**사진 크기를 안 적어서 내용이 밀립니다.** 위 예시처럼 `width`, `height`를 적어 두면 브라우저가 자리를 먼저 잡아 두어 CLS가 줄어듭니다. 늦게 뜨는 배너나 팝업이 본문을 밀어내는 것도 같은 원인이에요.

**외부 코드가 너무 많습니다.** 채팅 위젯, 지도, 여러 개의 분석 코드, 동영상 자동 재생이 쌓이면 휴대폰에서 느려집니다. 지금 실제로 쓰는 것만 남기세요. 다만 광고 성과를 재는 코드는 필요하니, 무엇을 남길지는 [GA4와 메타 픽셀 기초](/posts/ga4-meta-pixel-basics/)를 참고해 정리하면 됩니다.

**글꼴 파일이 무겁습니다.** 한글 웹폰트는 파일이 큰 편입니다. 굵기를 여러 개 불러오고 있다면 꼭 쓰는 한두 개로 줄여 보세요.

## 5. 숫자 말고 손으로 하는 점검

도구 점수가 좋아도 실제로 불편할 수 있습니다. 한 달에 한 번, 내 휴대폰으로 직접 확인하세요.

- [ ] 와이파이를 끄고 모바일 데이터로 열어 봤나요?
- [ ] 첫 화면에 제목과 신청 버튼이 바로 보이나요?
- [ ] 읽는 도중 글이 갑자기 아래로 밀리지 않나요?
- [ ] 신청 버튼과 전화 버튼을 눌렀을 때 바로 반응하나요?
- [ ] 사진을 새로 올린 뒤 다시 재 봤나요?

첫 화면에 무엇을 둘지 자체가 고민이라면 [랜딩페이지 구성 순서 7단계](/posts/landing-page-structure/)도 함께 보세요. 보여 줄 게 적을수록 페이지도 가벼워집니다.

## 정리

1. [PageSpeed Insights](https://pagespeed.web.dev/)에 **실제 랜딩페이지 주소**를 넣고 **모바일 결과**부터 봅니다.
2. 실제 사용자 데이터가 없으면 실험실 데이터로 보되, **고치기 전후를 여러 번** 재서 비교합니다.
3. **LCP 2.5초, INP 200밀리초, CLS 0.1** 이하가 '좋음' 기준입니다.
4. 작은 가게 페이지는 **사진 용량 줄이기, 사진 크기 적기, 안 쓰는 외부 코드 빼기**만 해도 대부분 좋아집니다.

광고를 켜기 전에 한 번, 사진을 바꿀 때마다 한 번. 이 두 번만 지켜도 들어온 손님을 놓치는 일이 줄어듭니다.
